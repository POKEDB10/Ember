# Architecture

## Phase 0 scaffold

Ember is a Java 17-compatible Swing desktop client and TLS server project, built with a JDK 21 toolchain and `javac --release 17`. Track B uses only JDK APIs. The package root is `edu.ember`; product identity lives in `AppInfo` so the name and tagline can be changed centrally.

The source layout separates shared protocol, model, security, and utility code from server, storage, client networking, Swing UI, tools, and a zero-dependency test runner. Later phases implement those packages behind the frozen interfaces below. `AppLog` provides named `java.util.logging` loggers. No Java serialization is permitted.

## Thread and UI rules

All Swing mutations run on the event dispatch thread. Network, disk, password hashing, and image decoding stay off the EDT. Server state locks protect short in-memory updates; blocking socket I/O is never performed while holding a state lock. Use named platform threads; virtual threads are future work.

## Build

Use `scripts/build.bat` or `scripts/build.sh`. Both compile with `--release 17 -encoding UTF-8 -Xlint:all,-serial -Werror`. `scripts/run-tests` runs the zero-dependency `EmberTestSuite`. The TLS server binds to `--bind` (default `0.0.0.0`); clients trust Ember's generated truststore and enable HTTPS endpoint identification. `WalStorageEngine` serializes writes through one synchronized method, checks record CRCs on replay, and truncates a torn last record. `SecurityAuditLogger`, `UserLockManager`, `AuthRateLimiter`, `TokenBucket`, and `AutoSaveThread` provide Phase 3 hardening.

The Phase 4 client persists commands before sending and drains the outbox after sync. Server duplicate handling is keyed by `(senderUserId, clientMsgId)`. Direct conversations and groups use server-side membership checks; group receipts aggregate recipient acknowledgements and update the sender's message status only when the full recipient count reaches DELIVERED or READ. The Swing entry point attaches `ReconnectManager` after a transport loss and resumes the stored session when it reconnects.

Phase 5's `client.ui` package contains the theme token strategy, font resolver, reusable custom-painted avatar/bubble surfaces, and the auth/chat/settings panels. `ChatWorkspacePanel` places the chat list beside the active conversation and settings card. `ConversationPanel` uses plain wrapping `JTextArea` message bodies, Enter to send, Shift+Enter for a newline, and listener-driven presence, typing, and receipts. `NotificationService` uses `SystemTray` when available and falls back to `ToastBanner`; both notification paths are triggered only when the window is unfocused.

Phase 6 adds public profiles, follow relationships, image uploads, posts, likes, comments, and feed/profile/post-detail views. `ImageValidator` checks PNG/JPEG signatures and uses `ImageReader.getWidth(0)` / `getHeight(0)` before pixel decoding; it rejects dimensions above 4096 on either side, or above 16 million pixels, then stores fresh RGB JPEGs and 300-pixel thumbnails. The server generates UUID file names and authorizes profile changes as self-only; feed, post, and media access return 404 for missing or unpublished objects. `StorageEngine` and the WAL persist social metadata; client file reads and Base64 preparation run off the EDT.

Phase 7 adds expiring messages, replies, six reactions, edit/delete, private accounts, follow approval, block/report, pins/stars/search, 24-hour stories, group polls, admin/report and group-info panels, forwarding, and snapshot compaction. `SearchEngine` matches all query tokens; `PollData` stores one vote row per group member. Story visibility follows private-account/block rules and uses `--story-ttl-sec` (default 86400). Admin names are configured explicitly with `--admin-user`; the default is no admins. WAL snapshots are checksummed GZIP event streams committed by atomic replacement before the covered WAL prefix is rotated. The replay path handles a crash between snapshot replacement and truncation and continues replaying later WAL records.

## Phase 8: proof, demo, and packaging

`AttackSimulator` uses real TLS sockets against an ephemeral local server and checks invalid framing, username validation, literal hostile text, forged sender fields, duplicate resend, and cross-user edit denial. `ConcurrencyStressHarness` creates ten headless clients, joins them to one group, sends 500 messages with concurrent senders, and checks history for message loss, duplicate IDs, and conversation/per-sender ordering; it repeats the run twice. `DemoSeeder` creates accounts and sample chat/social records and skips an already-seeded data directory. `EmberServer --demo-seed` seeds before server startup and enables Alice's admin role for this demo launch only.

The demo launch scripts start one server and three client profiles. `package-demo` builds executable JARs and `jpackage --type app-image` folders with bundled runtimes. The app-image invocation is documented in the README; no WiX installer is produced or required. The `.puml` diagrams correspond to implemented controller, connection-handler, storage, and model flows.

**Concepts:** real socket integration testing, concurrent producer ordering, idempotent fixtures, command-line options, JAR manifests, runtime bundling, and UML sequence/state/activity diagrams.

## Phase 9: website, multiple devices, and off-server storage

- **Multi-device.** `EmberServer.online` maps each user to a set of live connections. `sendToUser` fans an event out to every device and skips a failed one without disconnecting the sender; `removeOnline` reports offline presence only when the last device leaves. A sent message is also delivered to the sender's other devices.
- **One port, two clients.** `ConnectionHandler` peeks at the first bytes: `EMBR` is the desktop protocol, `GET `/`HEAD` goes to `WebGateway`, which serves the allowlisted static files, `/health`, and `/media/{id}` (session token required, cached by the browser for a year), or upgrades to a WebSocket. Each WebSocket message carries exactly one Ember frame. `permessage-deflate` compression keeps its window across messages; incoming messages are size-checked while they arrive and while they are inflated.
- **Web-only mode.** With `--no-tls` the server opens no TLS port and serves the website on `--http-port`/`--http-bind` behind a hosting proxy that terminates HTTPS. The login rate limiter then uses the last `X-Forwarded-For` address.
- **Desktop over the web.** `ClientController` works on a `ServerLink`: `TlsLink` (direct socket) or `WebSocketLink` (JDK `java.net.http.WebSocket`), chosen by `--url`.
- **Off-server storage.** `WalStorageEngine` optionally takes a `StorageReplica`. `BlobStoreReplica` queues every WAL record, uploads a batch every 2 s on one uploader thread, and replaces older logs with a snapshot after 1 MB of WAL. Files are GZIP-compressed (except images), AES-256-GCM encrypted with the logical name as associated data, split into parts below 4 MB, and committed with a marker so half-uploaded blobs are never read. Restore reads the newest complete snapshot plus every later log. A wrong key fails start-up instead of starting empty. `RootzBlobStore` implements `BlobStore` over the rootz.so REST API; tests use an in-memory fake.
- **Deployment.** `Dockerfile` (JDK build stage, JRE run stage, small heap, serial GC) and `render.yaml` (free web service, `/health` check, 120 s shutdown grace so pending uploads finish).
