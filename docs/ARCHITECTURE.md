# Architecture

## Phase 0 scaffold

Ember is a Java 17-compatible Swing desktop client and TLS server project, built with a JDK 21 toolchain and `javac --release 17`. Track B uses only JDK APIs. The package root is `edu.ember`; product identity lives in `AppInfo` so the name and tagline can be changed centrally.

The source layout separates shared protocol, model, security, and utility code from server, storage, client networking, Swing UI, tools, and a zero-dependency test runner. Later phases implement those packages behind the frozen interfaces below. `AppLog` provides named `java.util.logging` loggers. No Java serialization is permitted.

`PasswordHasher` and `FrameCodec` signatures were implemented in Phase 1. `StorageEngine`, `ClientModelListener`, `ClientController`, `LocalOutbox`, and `ReconnectManager` are implemented with the signatures above. Phase 4 adds persistent groups to the WAL, resumes sessions using a token after reconnect, syncs message deltas, pulls authorized history, and routes online presence, typing, ping/pong, and group receipt summaries. The WAL writes CRC-protected records and truncates an incomplete or checksum-invalid tail.

## Thread and UI rules

All Swing mutations run on the event dispatch thread. Network, disk, password hashing, and image decoding stay off the EDT. Server state locks protect short in-memory updates; blocking socket I/O is never performed while holding a state lock. Use named platform threads; virtual threads are future work.

## Build

Use `scripts/build.bat` or `scripts/build.sh`. Both compile with `--release 17 -encoding UTF-8 -Xlint:all,-serial -Werror`. `scripts/run-tests` runs the zero-dependency `EmberTestSuite`. The TLS server binds only to `127.0.0.1`; clients trust Ember's generated truststore and enable HTTPS endpoint identification. `WalStorageEngine` serializes writes through one synchronized method, checks record CRCs on replay, and truncates a torn last record. `SecurityAuditLogger`, `UserLockManager`, `AuthRateLimiter`, `TokenBucket`, and `AutoSaveThread` provide Phase 3 hardening.

The Phase 4 client persists commands before sending and drains the outbox after sync. Server duplicate handling is keyed by `(senderUserId, clientMsgId)`. Direct conversations and groups use server-side membership checks; group receipts aggregate recipient acknowledgements and update the sender's message status only when the full recipient count reaches DELIVERED or READ. The Swing entry point attaches `ReconnectManager` after a transport loss and resumes the stored session when it reconnects.

Phase 5's `client.ui` package contains the theme token strategy, font resolver, reusable custom-painted avatar/bubble surfaces, and the auth/chat/settings panels. `ChatWorkspacePanel` places the chat list beside the active conversation and settings card. `ConversationPanel` uses plain wrapping `JTextArea` message bodies, Enter to send, Shift+Enter for a newline, and listener-driven presence, typing, and receipts. `NotificationService` uses `SystemTray` when available and falls back to `ToastBanner`; both notification paths are triggered only when the window is unfocused.

Phase 6 adds public profiles, follow relationships, image uploads, posts, likes, comments, and feed/profile/post-detail views. `ImageValidator` checks PNG/JPEG signatures and uses `ImageReader.getWidth(0)` / `getHeight(0)` before pixel decoding; it rejects uploads above 5 MiB, dimensions above 4096 on either side, or above 16 million pixels, then stores fresh RGB JPEGs and 300-pixel thumbnails. The server generates UUID file names and authorizes profile changes as self-only; feed, post, and media access return 404 for missing or unpublished objects. `StorageEngine` and the WAL persist social metadata; client file reads and Base64 preparation run off the EDT.
