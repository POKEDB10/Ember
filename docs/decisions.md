# Decisions (calls v2)

Each entry: decision / why / alternative rejected.

1. **Desktop stays JDK-only; audio behind an `AudioCodec` interface.** / Zero-dependency laptop demo, explainable viva; Opus can be added later behind the same interface. / Concentus (pure-Java Opus) now: deferred to STRETCH.
2. **Desktop calls are voice-only; a video button hands the call to the website.** / The JDK has no camera API or video codec. / Native camera + codec libraries.
3. **Feature flag `calls.v2` = server flag AND client setting.** The server enables it with `--calls-v2` or `EMBER_CALLS_V2=1` and tells clients in `AUTH_OK` (`callsV2=true`); each client has a "Calls v2" setting (default on). v2 behaviour runs only when both are on; otherwise every legacy path runs unchanged. / Lets the demo fall back by flipping one switch on either side. / Client-only flag (server hand-off endpoints would still be live); server-only flag (no per-device escape hatch).
4. **Jitter-buffer sequence numbers reuse the existing per-sender packet counter** (already authenticated inside the encrypted header, strictly increasing per sender key). / No wire change, no new plaintext metadata. / A new sequence field inside the payload.
5. **Jitter buffer: `synchronized` methods over a sequence-ordered `TreeMap`, no blocking.** The network thread inserts; the mixer thread must produce a frame every 20 ms whether or not one arrived (then it conceals), so it must never block. / Ordering by sequence plus non-blocking take. / `BlockingQueue` (FIFO only, `take()` blocks the mixer); `wait/notify` (the mixer is clock-driven, not data-driven).
6. **JavaScript logic is tested with Node's built-in runner (`node --test`), no packages.** The quality-limit calculation and ladder live in a DOM-free `quality.js` shared by the page and the tests. `run-tests` runs them when `node` is installed and says "skipped" otherwise. / The web logic is where the video rules live; the Java runner cannot load it. / Porting the rules to Java just to test them (two copies drift); a JS test framework (dependency).
7. **Web stats log: in-memory ring of the last 300 samples with a "download" button; nothing persisted.** The desktop writes a rotating file log. / No personal data, no storage growth in the browser. / IndexedDB persistence.
8. **The voice codec is fixed when the call connects; a mode change mid-call applies to bitrates and video limits at once, and to the desktop's ADPCM rate (16/32 kHz) from the next call.** / The prompt requires both "fixed at connect" and "mode change applies in ≤ 2 s"; switching codec families mid-call would need a renegotiation round and risks a gap. / Re-negotiating the codec on every mode change.
9. **Calls v2 voice runs for 1:1 calls only; group calls keep the legacy pipeline even with the flag on.** / Group calls must stay untouched. / Sharing the new engine with group calls.
10. **Each side picks its own sending codec** (first entry of its policy preference that the other side announced it can play). / No extra round trip; both directions are always playable. / A single codec agreed for both directions (needs a negotiation handshake).
11. **Desktop audio devices are reached through small `Microphone`/`Speaker` interfaces** (Java Sound behind them). A device is opened at the best rate it offers (48, 44.1, 32, then 16 kHz); a failing device (exception, or ~100 ms of empty reads) is reopened, falling back to the system default, and the resamplers are rebuilt for its rate. / Testable unplug handling without real hardware; Bluetooth headsets that switch rates keep working. / Fixed 16 kHz lines straight from Java Sound (the legacy path).
12. **Resampler: polyphase windowed-sinc, 64 taps per phase, Blackman window, cut-off at 85 % of the lower Nyquist.** Measured in tests: passband (0.2–12 kHz) within 1 dB, stopband (17–23 kHz) at least 50 dB down for 48→32 kHz. / Real anti-aliasing at modest CPU (64 multiply-adds per output sample). / Linear interpolation (no anti-aliasing), a longer filter (more delay and CPU for no audible gain in speech).
13. **Calls v2 control messages (`caps`, `disp`, `vstat`, `vpause`, `vkey`) travel inside the existing end-to-end encrypted `ice` signal**, with `v: 2` and a type field. / The server already relays `ice` messages of varying size, so it learns nothing new ("no new plaintext metadata"), and older builds pass unknown `ice` payloads to WebRTC, which ignores them. / A new `ctl` signal kind (reveals a new message type to the server); reusing `relay` (older builds would switch the call to relay mode).
14. **The relay network estimate (`Ladder`) steps down from the rung actually in use**, and trouble is checked every second. / Measured: with the network estimate one rung above a mode-capped rung, the first visible step took 2.6 s (bar ≤ 2 s); after the fix 0.2 s. / A 2 s check with drops from the estimate.
15. **After a rung change, skipped frames are not counted as trouble for 1.5 s.** / The forced key frame after a change briefly backs up the socket; counted as congestion, it made the ladder drop straight back (seen live: up to 360p, down again 1.1 s later). / Raising the skip threshold for every frame.
16. **State messages (`vpause`, `disp`) that arrive faster than their rate limit are coalesced, not dropped.** / Seen live: a quick hidden→visible flicker lost the "visible" message, and the peer stayed paused. / Dropping all over-rate messages (fine for events like `vkey`, wrong for states).
17. **Video encoder watchdog:** an encoder that accepts frames but has produced nothing for 3 s, or reports an error, is replaced. / Seen live once after a long pause (31 frames/s in, nothing out, error swallowed); a fresh encoder with the same settings worked. Root cause not found. / Leaving the call without video until hang-up.
18. **Camera frame rate is measured from the frames the camera delivers (`MediaStreamTrackProcessor` on a copy of the track)**, falling back to `requestVideoFrameCallback`, then to the setting. / `requestVideoFrameCallback` counts frames drawn on screen, so it read 5 fps when the window was not being painted. / `requestVideoFrameCallback` only.
19. **Hand-off is two-phase with single-use tickets (30 s), bound to the device that asked and to the call.** Phase 1 (`handoff-prepare`) only issues a ticket; the browser then opens camera and microphone, so a refused permission leaves the desktop call untouched. Phase 2 (`handoff-commit`) swaps the device in one synchronized step; the first commit wins, the old device gets `end reason=elsewhere`, the other person gets `moved` and re-keys (new pair key, new sender key, new safety code). / Double-clicks, two tabs and stale links all fail safe. / One-step "take over" (a permission refusal would drop the call).
20. **A ticket presented by another device is ignored, not cancelled.** / Found by the race test: a second tab sending the first tab's token burned it, so the rightful tab failed too. / Burning the ticket on any use.
21. **`?join=<callId>` only shows a "Join call" button; nothing happens on page load.** The id is format-checked and removed from the address bar. / Links are untrusted (anyone can send one). / Auto-joining on open.
22. **A handed-off call continues on the relay.** / The desktop leg is always relayed, so the other side is already in relay mode; switching both sides to direct mid-call adds a renegotiation that could drop audio during the demo. Video on the relay follows the ladder (seen live: 360p start, 720p on Max). / Upgrading to direct WebRTC after the hand-off.
23. **For 5 s after joining by hand-off, a signal that does not decrypt is skipped instead of dropping the peer.** / Signals sealed for the old device can still be in flight when the swap happens. / Treating it as an attack (the call would break on every hand-off race).
24. **Each side re-sends its pause state every 2 s whenever it differs from what it last sent.** / Seen live under the throttle test: the "visible again" event never arrived, the other side stayed paused and video stopped for the rest of the call. After the fix a stray pause cleared in 0.7 s. / Relying on `visibilitychange` alone.
25. **Relay pings every 1 s (was 2 s).** / The round trip is the first trouble signal when a slow link's queue fills; measured with the throttling proxy, 2 s pings made the first step-down come 3 s after the drop, 1 s pings 1.8–2.8 s. Cost: a few bytes per second. / Faster pings (more packets for little gain); relying on socket back-pressure (never fired: the OS buffers on the path absorbed it).
26. **Relay throttling is tested with a JDK-only TCP proxy (`ThrottleProxy`) rather than Clumsy.** / Clumsy's packet driver needs administrator rights; the relay is TCP, so bandwidth, delay and queue size are what matter. / Clumsy (still needed for direct WebRTC over UDP; not done).
27. **Pictures and videos load through signed links listed with each post or story** (`/media/ID?v=f|t&e=…&s=…`, HMAC-SHA256, valid to the end of the next day, no session token or user name in the link). / The browser can then load media natively: in parallel, from its HTTP cache, and with byte ranges so videos start before they finish downloading and can seek. Measured: every request through the Cloudflare tunnel costs 0.5–1 s, so removing a header-authenticated fetch per picture matters. The older Bearer-header route still works. / Putting the session token in the URL; fetching every picture as a blob.
28. **Videos are checked, not re-encoded:** only MP4 and WebM, recognised by their first bytes and a matching name, at most 16 MB (and 60 s, checked in the browser). The poster frame is cut in the browser and goes through the normal image checks. / The JDK cannot decode or encode video; the browser plays the file in its own sandbox. / A video library on the server (breaks the JDK-only rule); accepting any file a browser might play.
29. **The desktop app shows a video's poster frame.** / Java has no video playback; the server substitutes the poster when the desktop asks for a video. / Downloading the whole video to the desktop for nothing.
30. **The browser's prompt/confirm pop-ups are replaced by themed in-app dialogs** (one `ask()` helper with inline validation, and a post/story composer with preview and real upload progress). / Pop-ups break the look, cannot validate, and block the page. / Keeping prompt().
31. **One key pair per account, sealed with the password and kept on the server ("account key backup").** The first device that signs in with the password makes it (the desktop app uploads its existing key), seals the private half with PBKDF2-SHA256 (600,000 rounds) + AES-GCM, binding account, device id and public key in as associated data, and stores only `kb1.<device>.<public>.<salt>.<iv>.<sealed>`. Every later password sign-in opens it, so every browser and desktop app of the account reads the same messages; the key a device used before is kept to read what was sealed for it. Same format in `e2e.js` and `E2eCrypto` (checked both ways). / Users saw "cannot be read on this device" after signing in again or in another browser: each browser had its own key and logout deleted it. / Device linking with a QR code (needs the old device at hand); a separate backup PIN (one more secret to remember). **Limit:** the server sees the password at sign-in, so an operator who logs passwords could open the backup; it protects against a stolen database, not a malicious server. Upgrade path: derive the sign-in secret on the device.
32. **Only a password sign-in may store the backup, and an existing backup is replaced only with `replace=1`** (after a password reset, when the old password no longer opens it). / A stolen session token must not swap in a key the thief knows. / Any signed-in session may set it.
33. **Logging out no longer retires the shared account key on the server; it only deletes the local copy.** / Retiring it would stop encryption for every other device of the account. / Retiring on logout as before.
34. **Email sign-up, sign-in and password reset by 6-digit code; the server stores only HMAC-SHA256(pepper, email).** Codes: single use, 10 minutes, 5 guesses, one email a minute per purpose, 5 per client address then one per 12 minutes, 300 an hour in total. Answers never say whether an address has an account: a used address gets a notice instead of a sign-up code, and a reset for an unknown address sends nothing. A reset signs out every other device. / "No new plaintext metadata on the server" still holds; recovery without an admin. / Storing the address (plaintext metadata); magic links (a link in a mailbox is a bearer token).
35. **Mail goes out through a small JDK SMTP client (implicit TLS on 465 or STARTTLS on 587, AUTH PLAIN, host name checked); without SMTP settings the code is printed on the server console.** / JDK-only rule; any provider with SMTP works (Gmail app password, Brevo, Resend). / JavaMail (dependency); a provider's HTTP API (ties the code to one vendor).
36. **Email stays optional at the protocol level.** The website's sign-up asks for it; the desktop app and older clients can still register without one and add it later. / The desktop sign-up screen was not changed. / Requiring it everywhere (breaks the desktop app).
37. **Posts and stories can be deleted by their owner** (two new WAL records). Signed links stop working at once because a link only serves media that a post or live story still shows; local files are deleted. / Users asked for it; a deleted post must not stay reachable. **Limit:** a copy already mirrored off-server (rootz) is not deleted.
38. **Relay queue guard (calls v2 flag on, 1:1 and group relay calls).** Above the best round trip seen, the extra is time spent queued on the way. Past 400 ms (from a ping answer, or from a ping still unanswered) video stops, voice continues; video resumes under 150 ms with a key frame, one rung lower. Backing up again within 10 s doubles the wait before the next try (2, 4, 8 s). Pings every 500 ms (250 ms while draining). / Measured: a tunnel or proxy that buffers seconds hides the backlog from the sender's socket; on a link that drops from 800 to 200 kbit/s with a 4 MB buffer the round trip rose to 17.4 s without the guard (median 8.8 s) and stayed at a median of 93 ms (max 1.17 s) with it (`docs/results.md`). / Socket back-pressure only (never fires behind a buffering proxy); the ladder alone (one step a second cannot outrun a queue that grows faster).
39. **Video decoder: after dropping a late frame, everything up to the next key frame is skipped and a key frame is requested.** / Decoding delta frames that refer to a dropped frame smears the picture until the next key frame (up to 4 s). / Dropping single frames (the old behaviour).
40. **Camera, microphone and raised hand are sent as a `state` control message inside the encrypted signal**; the others show an avatar instead of a frozen last frame, a muted icon, and raised hands first (in the order raised). Group calls open full screen; any call can toggle it. / Users saw the camera "not turn off": the other side kept showing the last frame. / A server-side state (new metadata).
41. **Message action buttons are built only for the selected message.** / A long chat carried about a dozen hidden buttons per message, all rebuilt on every update (150 messages ≈ 1,800 buttons). / Hiding them with CSS (the old way).
42. **Linking or changing the recovery email needs the current password, and the "signed in with the password" right (key backup) is tied to that account and cleared when a connection resumes with a token.** / Found by a security review: a stolen session could otherwise move account recovery to the thief's email, and a connection that resumed another session kept the right. / Code to the new address only (proves the address, not the person).
